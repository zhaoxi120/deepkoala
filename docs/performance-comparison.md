# 取消窗口残基限制后的性能与使用兼容性

日期：2026-10-26（Asia/Tokyo）。已移除每窗口 4,000,000 残基限制，默认只按 4096 条序列分窗。
GPU 每批的显存预算、长度预算、OOM 拆批和可选 CPU fallback 保留。

结论：这次修改允许长序列组成更大的排序窗口，但没有证明所有输入都会提速。
真实混合长度数据的预热后推理阶段较原版快约 1.45 倍；本次完整命令行耗时基本持平。
等长超长序列没有明显提速，动态大 batch 明显增加 GPU 显存使用。

## 测量方法

同一张空闲 A100 80GB、PyTorch 2.4.1+cu121、CUDA 12.1、cuDNN 90100、FP32，
使用同一套真实 `202502/full` 权重，简化输出、top-k=1。比较四种实现：

1. GitHub 原版：提交 `f246bb9680531372d86d72e6b9b072fee13fc5b5`，全量读取，固定 batch=32、workers=2。
2. 当前流式固定模式：`memory_preset="off"`，相同 batch=32、workers=2。
3. 取消限制前快照：CUDA 自动分批，4096 条窗口且有 400 万残基限制。
4. 当前版本：CUDA 自动分批，4096 条窗口，无累计残基限制。

当前版本还包含下文的输出权限兼容修复，取消限制前快照不包含该修复，
因此两者并非严格只改变一个变量的实验。

三组输入分别为真实 FASTA 的前 8192 条（平均约 527 aa、最长 5105 aa），
512 条各 16384 aa 的等长合成压力输入，以及 `fasta/case.fasta` 的 2 条输入。
每个方案、每组数据执行三次独立进程并轮换顺序，共 36 次 API 测量；
另对原版和当前版各执行三次真实 CLI，共 18 次。总计 54 次。

API 测量先执行相同的小 GRU 预热，再单独计时 `inference()`，包含模型重新加载、输入解析、
自动校准（如启用）、推理及 CSV 输出。CLI 直接运行原生命令，计时包含 Python/import、CUDA
初始化和模型加载。两种口径不能混用。未人为清空操作系统文件缓存；只有三次重复，不能把小差异当作确定收益。

## 用户实际命令行耗时

单位：秒，三次中位数；括号为最小–最大。

| 输入 | GitHub 原版 | 当前自动分批 |
| --- | ---: | ---: |
| 真实 8192 条 | 4.223（4.222–4.374） | 4.223（3.471–4.824） |
| 512 × 16384 aa | 4.123（4.031–7.035） | 4.324（4.322–5.476） |
| 2 条小文件 | 3.431（3.279–4.172） | 3.021（2.871–6.025） |

真实数据完整命令行中位数持平；长序列样本当前约慢 4.9%。启动波动明显，
尤其不能仅凭小文件中位数就推断稳定加速。

## 预热后推理阶段

单位：秒，三次中位数。

| 输入 | GitHub 原版固定 | 当前流式固定 | 原动态：有残基限制 | 当前动态：无残基限制 |
| --- | ---: | ---: | ---: | ---: |
| 真实 8192 条 | 1.385 | 1.652 | 0.968 | 0.958 |
| 512 × 16384 aa | 1.163 | 1.233 | 1.238 | 1.198 |
| 2 条小文件 | 0.415 | 0.433 | 0.123 | 0.132 |

真实数据当前比 GitHub 原版少用约 30.8% 推理时间，速度约为 1.45 倍。
等长超长序列当前比原版约慢 3.0%，没有显示加速。
仅比较取消限制前后，长序列从 1.238 秒到 1.198 秒，约减少 3.2%，但测量范围重叠，
不能认定存在稳定提升。该输入由原来的三个窗口变成一个窗口，实测最大 batch 从 244 增至 257。

## 显存与主机内存

PyTorch `reserved` 峰值，单位 GiB，为三次 API 测量中位数，包含分配器缓存；
不等于张量实际占用，也不包含所有 CUDA 驱动/库内存。

| 输入 | GitHub 原版 | 当前流式固定 | 原动态有残基限制 | 当前动态无残基限制 |
| --- | ---: | ---: | ---: | ---: |
| 真实 8192 条 | 4.764 | 4.750 | 49.535 | 49.535 |
| 512 × 16384 aa | 8.430 | 4.383 | 33.191 | 34.961 |

对应真实数据的 `allocated` 峰值为原版 1.388 GiB、当前动态 21.544 GiB；
长序列为原版 4.358 GiB、当前动态 34.690 GiB。因此动态 batch 的性能收益伴随明显显存开销，
不应描述成同时普遍节省 GPU 内存。A100 自动选择 `gt32`，调度预算为 51.2 GiB。
可用较保守的预设或显式 batch 上限降低使用量，固定模式也仍可用。

本次 GPU 推理父进程 RSS 约 0.9 GiB，模型/运行库开销占较大部分；固定模式另外启动两个 worker。
报告里的“进程树 RSS 求和”会重复计算共享页，不能据此宣称节省了等量物理 RAM。

另用相同的 4096 条 × 16384 aa 输入单独测量读取内存，三次独立进程的中位数如下：

| 指标 | 原版全量读取 | 原 400 万限制 | 当前 4096 条窗口 |
| --- | ---: | ---: | ---: |
| 原始序列字符 | 64 MiB | 64 MiB | 64 MiB |
| Python 分配峰值 | 132.12 MiB | 7.91 MiB | 68.87 MiB |
| 整个读取进程 RSS 峰值 | 331.64 MiB | 206.63 MiB | 269.35 MiB |
| 相对读取前的 RSS 增长 | 128.77 MiB | 3.85 MiB | 67.03 MiB |

这里只运行读取器，不包含模型推理、tokenization 或 GPU。
64 MiB 是这组长度下的序列内容，不是通用的总内存上限；序列更长，窗口内存仍会增加。

## 输出验证与限制

54 次性能测量均成功完成，所测简化 CSV 与对应原版参考逐字节一致。
这只能证明这些输入与简化输出的兼容性，不保证任意输入的详细浮点结果完全一致。

取消限制后的 16384 aa 七档额外回归中，2/4/8/16/24/32 档通过；
`gt32` 的严格详细概率检查未通过原定 0.0005 容差：第一个 257 条 batch 的第三名
`K19632` 概率由 0.1054 变为 0.1060，差 0.0006，共 257/1536 个概率单元超过容差。
该 KO 阈值为 0.9994；所测标签、顺序、阈值、注释均一致，简化 CSV 仍完全相同。
`gt32` 推理正常完成，显存检查通过，零 OOM、零 CPU fallback；
另外的混合输入默认 `auto` 验证也通过。七档容量通过 A100 上的测试用分配器限额模拟，
不能替代七种实体显卡的硬件兼容性测试。
未放宽断言、未修改预测来掩盖差异，失败记录保留。此前手动 batch=7 的近似并列 KO 排名互换
也说明分组改变后不保证详细 top-k 结果完全一致。需要原分批方式时使用 `--memory-preset off`。

## 使用方式与回归

原来的命令和 Python 参数仍可用，新增参数均可选。但 CUDA 默认行为不同：自动选档、
4096 条内排序、动态分批；显式 batch_size 成为上限，num_workers 只在固定模式使用。
CPU/MPS、固定模式和多域模式保持原策略。Python 返回值保留原键，自适应模式增加 `batching`。

```bash
# 原命令继续可用，CUDA 默认自动调度
python -m deepkoala.cli -i proteins.fasta -o results.csv

# 恢复原固定分批方式，保留流式读写
python -m deepkoala.cli -i proteins.fasta -o results.csv --memory-preset off
```

兼容性检查还修复了原子写出文件权限的问题：新文件遵循 umask，覆盖已有文件时保留权限位；
写入中的临时文件保持私有。原子替换的链接与 inode 语义及其他兼容细节见
[使用兼容性说明](usage-compatibility.md)。

最终 CPU 回归：**231 passed、4 skipped、5 xfailed**；跳过/预期失败均为已有范围。
这与上述额外 GPU 详细概率检查的失败分别记录，不能合并宣称“所有测试全部通过”。
