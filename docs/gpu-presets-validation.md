## 实现与预算

| 档位 | 名义容量 GiB | 80% 总预算 GiB |
| --- | ---: | ---: |
| `2` | 2 | 1.6 |
| `4` | 4 | 3.2 |
| `8` | 8 | 6.4 |
| `16` | 16 | 12.8 |
| `24` | 24 | 19.2 |
| `32` | 32 | 25.6 |
| `gt32` | 64 | 51.2 |

`gt32` 是 32 档的两倍。默认根据设备总显存自动选档；再按实际容量及启动时空闲显存收紧预算。
例如 40 GiB 卡即使选 `gt32`，预算仍限制为至多 32 GiB。名义容量允许 5% 的设备报告差异。

预算包含模型、推理张量、缓存，以及 0.75 GiB 的 CUDA 上下文/库开销预留。
实际加载模型后执行三个小规模校准，估算每个 padded residue 的峰值开销，并增加余量，
同时单独预留 batch × 分类数对应的输出内存。默认最大 batch 为 512，用户指定值始终作为上限。

80% 是**批次调度目标，不是进程级分配器硬上限**。它不会强制把显存填满；
不同架构、cuDNN 工作区和其他进程仍可能导致瞬时超出目标或 OOM。
程序不修改调用者的全局 CUDA allocator fraction；PyTorch 2.4.1 无读取/恢复该值的接口。

CUDA 当前默认使用最多 4096 条的窗口，窗口内按长度排序，然后恢复输入顺序。
不再设置窗口累计残基上限，不截断、不丢弃序列。OOM 时释放失败现场，拆批重试，
并下调后续批次预算。单条仍无法处理时默认明确报错；指定 `--oom-fallback cpu` 可回退到 CPU。
CPU 回退仅针对序列推理，不处理 CUDA 初始化或首次模型加载失败。

回退不会按 `32 → 24 → 16 GiB` 逐档降级。预设在初始化时确定；对一个包含 B 条、最长 L aa 的
失败批次，将 padded-residue 上限降为 `min(旧上限, max(1, floor(B×L/2)))`，然后把记录拆成两半重试。
例如 `8×4096 aa` 失败后降为最多 16384 padded residues，按 `4+4` 条重试；继续失败则再拆小。
成功推理但峰值超过调度目标也会降低后续上限。单次运行内只下调，不自动恢复；短序列仍可组合出
更多条的 batch。空闲显存仅在初始化时查询，之后依据实测峰值和 OOM 调整长度预算。

CPU/MPS 和 `--memory-preset off` 保留固定批次流式读取；多域模式保持原实现。

## 前台 A100 实测

使用前台空闲的 NVIDIA A100 80GB PCIe 完成，不需要向 PBS/APG 提交任务。
运行环境：PyTorch 2.4.1+cu121、CUDA 12.1、cuDNN 90100、FP32、eval/no_grad，真实 `202502/full` 模型。
CUDA 报告实际可见容量为 79.25 GiB。

每档独立进程设置测试用 allocator 硬限额：该档预算减去 0.75 GiB。
这模拟显存容量限制，不能替代七种实体显卡、驱动及架构的兼容性测试。

输入包括 96 条混合长度序列（1–8192 aa，重复 ID，多个窗口），以及 512 条各 8192 aa 的压力输入。
基线为同一 CUDA 模型的固定 batch=8 推理。下表是压力输入测量值；实际 batch 由数据长度和校准决定，
不是写死在预设中的 batch size。

| 档位 | 实测最大 batch | PyTorch 峰值 reserved GiB | 加 0.75 GiB 预留后 | 预算 GiB |
| --- | ---: | ---: | ---: | ---: |
| 2 | 6 | 0.439 | 1.189 | 1.6 |
| 4 | 23 | 1.602 | 2.352 | 3.2 |
| 8 | 56 | 3.840 | 4.590 | 6.4 |
| 16 | 121 | 8.254 | 9.004 | 12.8 |
| 24 | 187 | 12.732 | 13.482 | 19.2 |
| 32 | 253 | 17.230 | 17.980 | 25.6 |
| gt32 | 488 | 33.193 | 33.943 | 51.2 |

七档全部完成，所测标签、阈值、注释决定、记录数和顺序与基线一致；正常压力测试未触发 OOM 或 CPU 回退。
分组改变带来小幅 FP32 差异，四位小数概率最大差为 0.0002，比较容差为 0.0005。
这不保证任何输入在阈值边缘都作出相同决定；需要固定批次行为时使用 `--memory-preset off`。

额外真实故障测试：

- 自动选档识别 A100 为 `gt32`；显式 batch_size=7 的上限生效。
- 校准后把独立测试进程限到 256 MiB，512 条 × 4096 aa 触发 7 次真实 CUDA OOM，
  自动降至每批 4 条后完成；无漏行、重行或乱序，与参考预测一致。
- 单条 4096 aa 在 40 MiB 测试限额下触发真实 OOM，成功回退 CPU，预测与 CPU 参考一致。
- `202502/frag` 模型的 2 GiB 档也通过 96 条混合长度输入对照：标签与注释一致，
  概率最大差 0.0001；PyTorch reserved 峰值 504 MiB，加预留后为 1.242 GiB。
- 真实 `python -m deepkoala.cli` 入口未指定 batch/preset 时自动选择 `gt32`，batch 上限 512；
  完成 2 条输入、6 行 top-k 输出，日志与 CSV 计数一致。

结束时已确认 A100 无残留计算进程、显存占用为 0 MiB。详见
[`GPU 原始测试报告`](../test-results/gpu-presets/REPORT.md)。

## 16384 aa 补充压力测试

按用户要求将单条长度翻倍，保持 512 条输入，使用默认 4096 条窗口。
400 万残基上限将输入分成 `244 + 244 + 24` 条三个窗口，再按各档预算动态分批。
混合输入仍为 96 条，并增加 16384 aa 序列。旧的 8192 aa 输入、CSV 和报告保留。

| 档位 | 8192 aa 最大 batch | 16384 aa 最大 batch | 16384 aa PyTorch 峰值 reserved GiB |
| --- | ---: | ---: | ---: |
| 2 | 6 | 3 | 0.439 |
| 4 | 23 | 11 | 1.533 |
| 8 | 56 | 28 | 3.840 |
| 16 | 121 | 60 | 8.184 |
| 24 | 187 | 93 | 12.664 |
| 32 | 253 | 126 | 17.158 |
| gt32 | 488 | 244 | 33.191 |

七档默认参数的压力输入均完成，无 CPU 回退，所测标签、阈值、注释与顺序均与固定 batch=8 基线一致。
上表峰值加 0.75 GiB CUDA 预留后仍低于相应预算。长序列压力输入的四位小数概率最大差为 0.0001。

4 GiB 档的混合输入触发了 1 次真实 CUDA OOM：11 条序列的批次失败后，长度预算从 185293
降到 90112，再拆批完成全部 96 条。原测试的“必须零 OOM”断言因此失败；首轮日志已保留。
补充压测显式启用 `--allow-recovered-oom`，允许成功恢复的 OOM，仍严格检查输出、概率容差、
已分配峰值预算和无意外 CPU fallback。其他档位混合输入以及所有档位纯长序列输入没有 OOM。
显存峰值不包含被分配器拒绝的内存申请，因此发生 OOM 时，已记录峰值仍可能低于预算。

独立诊断中，该失败批次含 11 条、长度 4096–16384 aa，共 180224 padded residues。
错误报告显示已有约 1.27 GiB 未使用缓存，又申请约 1.39 GiB 新块，与测试的 2.45 GiB allocator
限额产生冲突。清理缓存后，同一 11 条在同一限额下整批成功，reserved 峰值为 1.533 GiB，
与参考标签一致。这支持“已有缓存块与形状变化的大分配交互”的解释，不能据此断言
11 条的实际工作集必然超过预算。程序现有清缓存、拆批路径正常恢复，生产策略未改。

默认 `auto`（未手动指定 batch size）另行验证通过：识别 `gt32`，处理全部 96 条，
标签、注释、顺序均与固定基线一致，没有 OOM 或 CPU 回退。

额外手动 `batch_size=7` 对照未满足严格标签一致性：混合输入的一条 32 aa 短序列上，
两个近似并列且低于注释阈值的 KO 排名互换，最终注释决定未变。未放宽标签断言，也未修改
生产预测逻辑来掩盖差异。改变 batch 形状可能影响 FP32 的近似并列排名，详细 top-k 结果
不能保证逐字相同；需要原固定批次行为时使用 `--memory-preset off` 并固定 batch size。

具体为第 15 条输入（零基序号 14）：`K18193` 与 `K10249` 交换 top-1/top-2，第三名
`K13865` 不变。前两者概率约 0.077，明显低于相应阈值 0.8699 和 0.7381。
全部 288 行转成简化输出（未注释标签置空）后完全一致；详细 top-k 标签的严格失败仍保留。

16384 aa 的真实 OOM 回退也已验证：512 条在测试用 256 MiB allocator 限额下经历 7 次 OOM，
最终每批 1 条全部完成，与 GPU 单条参考的概率一致；单条在 40 MiB 限额下触发 1 次 OOM，
成功回退 CPU。这些极低限额只用于故障注入，不代表 2 GiB 预设下需要单条运行。

完整补充结果保存在 [`test-results/gpu-presets-16384/`](../test-results/gpu-presets-16384/)。

```bash

```

## 使用

普通 CUDA 命令默认自动选档、校准、排序和拆批，通常无需配置 batch。

```bash
python -m deepkoala.cli -i proteins.fasta -o results.csv --device cuda --oom-fallback cpu
```

可用 `--memory-preset 8` 手动选更保守的档位，`--batch_size 128` 设置条数上限，
`--max-padded-residues` 设置更低的长度预算。Python API 返回的 `batching` 字典包含选档、预算、
校准与生产推理的峰值（包括失败尝试）、OOM 次数和 CPU 回退次数。
